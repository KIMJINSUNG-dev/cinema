# Cinema 설계 결정 기록

> 최초 작성: 2026-10-01 · 최종 수정: 2026-10-26

Cinema 개발 중 내린 설계 결정과 그 근거를 기록합니다.
새 결정이 생기거나 기존 결정이 바뀌면 이 문서에 추가하고, 바뀐 결정은 지우지 않고 변경 내역을 남깁니다.

각 항목은 **결정 / 근거 / 검토한 대안** 순서로 작성합니다.

## 1. 기술 스택 · 프로젝트 구조

### D-01. Spring Boot 4.1.1 + Java 17, 설정은 application.properties

- **결정**: Spring Boot 4.1.1, Java 17을 사용하고 설정 파일은 `application.properties`로 작성한다.
- **근거**: 최신 기술보다 안정성과 실무 환경을 우선한다. QueryDSL(OpenFeign 포크)이 Spring Boot 4.1.x와 호환되는 것을 확인했다.
- **검토한 대안**: 최신 Java 버전 — 실무 환경과의 거리, 라이브러리 호환성 부담으로 제외.
- **보완 (2026-10-23, JDK 보안 패치)**: Java 17의 메이저 버전은 유지하되, 보안 패치(17.0.x)는 따라간다.
  - 계기: CVE-2026-91403(CVSS 9.1, 2026-10-21). JDK 기본 신뢰 인증서 목록(`cacerts`)에 개인키를 공개키로부터 계산할 수 있는 eMudhra 중간 CA 8개가 포함되어, 공격자가 만든 인증서를 Java가 신뢰한다. Java가 외부에 TLS로 접속할 때 통신 가로채기 · 조작이 가능하다. Java 17은 17.0.21 이하가 영향을 받는다.
  - 현재 영향: 외부 TLS 연결이 없어(MySQL · Redis 로컬) 실질적 위험은 낮다. CI의 Temurin 17.0.20도 영향 범위이나 코드 수정은 필요 없다.
  - 조치: 패치된 Temurin 17이 배포되면 로컬 JDK를 갱신한다. CI는 `java-version: '17'`이 최신 17을 받으므로 workflow 수정 없이 로그의 JDK 버전만 확인한다. 외부 TLS 연결이 생기는 6단계(이메일) · 7단계(PG) 착수 전에 패치 적용을 반드시 확인한다.
  - 10/23 확인: Temurin 17의 10월 릴리스(17.0.21)는 아직 배포 전(Adoptium 릴리스 현황 기준).

### D-02. 백엔드 · 프론트엔드 분리 레포

- **결정**: 백엔드(`cinema`)와 프론트엔드(`cinema-frontend`)를 별도 레포로 관리한다.
- **근거**: 각 레포의 빌드 · 테스트 · AI 작업 규칙(`CLAUDE.md`)을 독립적으로 관리할 수 있다.
- **검토한 대안**: 모노레포 — 단일 레포 안에서 빌드 · CI 설정이 복잡해짐.

### D-03. 민감 정보는 환경변수로 분리

- **결정**: DB 비밀번호와 JWT secret은 `application.properties`에 값으로 쓰지 않고 환경변수 플레이스홀더(`${CINEMA_DB_PASSWORD}`, `${CINEMA_JWT_SECRET}`)로 참조한다. 로컬에서는 Windows 사용자 환경변수로 등록하고, 플레이스홀더에 기본값은 두지 않는다. 그 외 설정은 실제 값 그대로 커밋한다.
- **근거**: 민감 정보가 커밋에 포함될 위험을 없앤다. IDE 실행 구성이 아닌 OS 환경변수로 등록해 IDE · Gradle · 터미널 어디서 실행해도 같은 값이 적용되게 하고, CI(GitHub Actions)에서도 Secrets로 같은 이름의 값을 주입할 수 있다. `CINEMA_` 접두사는 다른 프로젝트와의 변수 이름 충돌을 막기 위함이다.
- **검토한 대안**: `.gitignore`에 등록한 로컬 전용 설정 파일 — CI에서 별도 파일 생성이 필요함. IDE 실행 구성에만 등록 — 그 실행 구성 밖(Gradle 테스트 등)에서는 값이 주입되지 않음.

## 2. 도메인 설계

### D-04. 좌석 등급은 Enum이 아닌 엔티티(SeatGrade)

- **결정**: 좌석 등급을 `SeatGrade` 엔티티로 설계하고, 관리자가 등급 이름과 기준 가격을 직접 등록한다.
- **근거**: 등급이나 가격이 바뀔 때 코드 수정 · 재배포 없이 데이터로 관리할 수 있다.
- **검토한 대안**: Enum — 등급 추가 · 가격 변경 시마다 코드 수정이 필요함.

### D-05. 상영관은 삭제하지 않고 상태로 관리

- **결정**: `Screen`에는 삭제 기능을 두지 않고 `ActiveStatus`(ACTIVE / MAINTENANCE / CLOSED)로 대체한다. 기본값은 CLOSED다.
- **근거**: 좌석 · 상영 일정 · 예약이 상영관을 참조하므로 참조 무결성과 이력 보존이 필요하다. 기본값을 CLOSED로 두어 설정이 끝나지 않은 상영관이 노출되지 않게 한다.
- **검토한 대안**: 물리 삭제 — 연관 데이터가 깨지거나 함께 삭제됨.

### D-06. 영화의 상영 상태와 노출 여부를 별도 축으로 분리

- **결정**: `MovieStatus`(상영 일정 기준 상태)와 `DisplayStatus`(사용자 화면 노출 여부)를 분리한다.
- **근거**: "상영 예정이지만 아직 공개하지 않음"처럼 두 상태가 독립적으로 바뀌는 경우가 있다.
- **검토한 대안**: 하나의 상태값으로 통합 — 상태 조합이 늘어날수록 값이 복잡해짐.

### D-07. 다대다 관계는 중간 엔티티로 해결

- **결정**: 영화–장르는 `MovieGenre`, 예약–좌석은 `ReservationSeat` 중간 엔티티로 연결한다. `MovieGenre`는 update 메서드 없이 불변 연결로 설계하고, 장르 변경은 기존 연결 삭제 후 재생성으로 처리한다.
- **근거**: 중간 테이블에 추가 정보(예: 좌석별 결제 금액)를 담을 수 있고, 연결 자체를 명시적으로 다룰 수 있다.
- **검토한 대안**: `@ManyToMany` — 중간 테이블에 컬럼을 추가할 수 없음.

### D-08. 결제 금액은 ReservationSeat에 저장

- **결정**: 좌석별 결제 금액을 `ReservationSeat`에 저장하고, 금액 계산은 서비스 계층에서 처리한다. 현재는 좌석 등급별 차등만 반영한다.
- **근거**: 등급 기준 가격이 나중에 바뀌어도 이미 예매된 금액은 예매 당시 값으로 유지되어야 한다.
- **검토한 대안**: 조회 시점에 SeatGrade 가격으로 계산 — 가격 변경 시 과거 예매 금액이 달라짐.
- **추후 확장**: 회원 등급 할인, 시간대별 할증.
- **보완 (2026-10-26)**: 가격은 예약 좌석을 만들 때 받아 고정하고 `updatePrice()`를 삭제했다. 변경 메서드가 열려 있으면 예매 후에도 가격을 바꿀 수 있어 "예매 당시 값 유지"가 코드로 보장되지 않았다. 계산(등급 기준 가격, 이후 할인)은 서비스가 하고 엔티티는 음수만 거부한다.

## 3. 엔티티 작성 원칙

### D-09. 엔티티에 @Builder를 적용하지 않음

- **결정**: 엔티티 생성은 생성자로, 변경은 검증 로직을 가진 update 메서드로만 한다.
- **근거**: `@Builder`를 쓰면 생성자와 update 메서드에 둔 검증 로직을 우회해 객체를 만들 수 있다.
- **보완 (2026-10-07)**: 같은 이유로 JPA용 기본 생성자는 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`로 제한한다. JPA와 프록시는 protected 이상의 기본 생성자가 필요하지만, public이면 검증을 거치지 않은 빈 객체를 어디서든 만들 수 있다. (Seat 우선 적용, 다른 엔티티는 점검 예정)
- **검토한 대안**: `@Builder` + 별도 검증 — 검증 위치가 분산됨.

### D-10. 필수 연관관계는 생성자로 받고 변경 불가

- **결정**: `Reservation`(회원 + 상영 일정), `ReservationSeat`(좌석 + 예약)처럼 바뀌면 안 되는 필수값은 생성자로만 받는다.
- **근거**: 생성 이후 예약의 주인이나 좌석이 바뀌는 상황을 구조적으로 막는다.

### D-11. 공통 생성 · 수정 일시는 BaseEntity로 관리

- **결정**: `@MappedSuperclass` + JPA Auditing 기반 `BaseEntity`를 모든 엔티티에 적용한다.
- **근거**: 생성 · 수정 일시 관리 코드의 중복을 없앤다.

## 4. 회원 · 권한

### D-12. 권한은 4단계 Role + RoleHierarchy

- **결정**: `ADMIN > MANAGER > STAFF > CUSTOMER` 4단계로 두고, 상위 권한이 하위 권한을 포함하도록 `RoleHierarchy`로 구성한다. 로그인 여부는 Role이 아니라 엔드포인트 인증 설정으로 구분한다.
- **근거**: 매표소 직원(STAFF)의 예매 처리, 관리자(MANAGER)의 콘텐츠 관리, 최고 관리자(ADMIN)의 직원 계정 관리처럼 역할이 계층적으로 겹친다.
- **검토한 대안**: 비로그인 상태를 별도 Role(예: GUEST)로 두는 구조 — 로그인 여부는 Spring Security의 인증 여부로 이미 구분되므로, Role에 같은 정보를 중복 표현할 필요가 없어 제외.

### D-13. 회원 정보 수정 경로를 권한별로 분리

- **결정**: ADMIN은 일괄 수정(PUT + `MemberUpdateRequest`), CUSTOMER는 닉네임 변경 · 탈퇴 개별 엔드포인트(PATCH + 전용 DTO)를 사용한다. `emailVerified`는 외부 수정 경로에서 모두 제외한다.
- **근거**: 사용자가 수정할 수 없어야 하는 필드(권한, 인증 여부)가 요청으로 바뀌는 것을 DTO 단계에서 막는다.

### D-14. 본인 리소스는 소유권 검증

- **결정**: 본인만 수정할 수 있는 API는 요청자(`@AuthenticationPrincipal`)와 대상 회원을 비교하고, 불일치 시 `AccessDeniedException`(403)을 던진다.
- **근거**: 로그인 여부만 확인하면 다른 회원의 id로 요청을 보낼 수 있다.
- **보완 (2026-10-15)**: 
  - 서비스에서 던진 `AccessDeniedException`은 보안 필터가 아니라 `GlobalExceptionHandler`가 먼저 잡는다. 전용 처리기가 없어 `Exception.class` 처리기에 걸려 500이 나가던 문제를 발견해, 403을 돌려주는 처리기를 추가했다(D-35).
  - 로그아웃도 같은 원칙을 적용한다. 대상 회원(email)을 요청 본문이 아니라 토큰의 주인(`@AuthenticationPrincipal`)에서 가져온다. 본문에서 받으면 다른 회원의 email과 기기 id로 그 회원의 세션을 삭제할 수 있었다.

## 5. 인증 (JWT · Redis)

### D-15. Tangerine 인증 인프라 재사용

- **결정**: `JwtProvider`, `RateLimitService`, `RedisConfig`, `GlobalExceptionHandler`, `JwtAuthenticationFilter`를 Tangerine에서 포팅한다. 동작 원리는 한 줄씩 분석한 뒤 이식한다.
- **근거**: 이미 검증된 구조이며, Cinema 고유의 판단이 필요한 부분이 적다.

### D-16. Refresh Token은 HttpOnly 쿠키로 전달

- **결정**: Refresh Token은 응답 본문이 아닌 HttpOnly 쿠키로 전달한다. 로그인 응답에서는 null 필드를 제외한다.
- **근거**: JavaScript에서 접근할 수 없어 XSS로 인한 토큰 탈취를 막는다.
- **검토한 대안**: 응답 본문 + 클라이언트 저장 — XSS에 노출됨.

### D-17. 로그인 세션은 기기 단위로 관리

- **결정**: Redis 키를 `이메일 + deviceId` 구조로 설계해 다중 기기 로그인을 허용한다. deviceId는 토큰에 넣지 않고 요청마다 별도로 전달한다. Redis TTL은 `jwt.refresh-expiration` 설정값과 연동한다.
- **근거**: 업계 관행이 다중 기기 허용이며, 기기별 로그아웃 등으로 확장할 수 있다. deviceId는 보안 요소가 아니라 Redis 키 식별용이다.
- **검토한 대안**: 이메일 단위 단일 세션 — 다른 기기 로그인 시 기존 세션이 끊김.

### D-18. 토큰 재발급 시 role은 DB에서 재조회

- **결정**: role은 Access Token에만 담고, Refresh Token으로 재발급할 때는 DB에서 최신 role을 다시 읽는다.
- **근거**: Refresh Token은 수명이 길어서, 그 사이 권한이 변경(강등 · 승격)될 수 있다. 이전 토큰의 role을 그대로 복사하면 바뀐 권한이 Refresh Token 만료 전까지 반영되지 않는다.
- **검증 (2026-10-02)**: CUSTOMER 계정의 role을 DB에서 MANAGER로 변경한 뒤 MANAGER 전용 API를 호출했다. 기존 Access Token으로는 403, 재발급받은 Access Token으로는 호출에 성공했다. `JwtAuthenticationFilter`는 요청마다 DB를 조회하지 않고 토큰의 role 클레임으로 권한을 만들기 때문이다.
- **한계**: 권한 변경이 반영되지 않는 최대 시간은 Access Token의 만료 시간과 같다. 그래서 Access Token의 수명은 짧게 유지한다. 강등을 즉시 반영해야 한다면 토큰 블랙리스트 등을 확장 단계에서 검토한다.

## 6. 개발 순서 · 범위

### D-19. 예약 기능을 이메일 인증보다 먼저 구현

- **결정**: Seat · SeatGrade · Showtime → 예약 · 동시성을 먼저 진행하고, 이메일 인증 · 비밀번호 재발급 · 아이디 찾기는 PG 연동 직전에 착수한다.
- **근거**: 예약이 프로젝트의 핵심이자 다른 기능의 전제 조건이다. 이메일 인증의 원래 목적(결제 보안)은 PG 연동 전까지만 갖추면 된다.

### D-20. 좌석 동시성은 DB 락으로 시작

- **결정**: 최소 완성본에서는 DB 락으로 좌석 동시 예약을 처리하고, Redis 기반 처리는 확장 범위로 둔다.
- **근거**: 먼저 안전하게 동작하는 구현을 확보한 뒤 성능을 개선한다.

### D-21. QueryDSL은 예약 기능 직후, 통합 테스트 · CI는 예약 기능 이전

- **결정**: 로드맵 3장 참고.

## 7. 좌석 · 좌석 등급 API

### D-22. 좌석은 삭제하지 않고 상태로 관리, 구조 변경은 상영관 교체로 처리

- **결정**: 좌석에는 삭제 기능을 두지 않는다. 고장 등 좌석 단위 문제는 `SeatStatus`(ACTIVE / DEACTIVATED)로 처리하고, 상영관 좌석 배치를 전면 변경할 때는 새 상영관을 만들고 기존 상영관을 비활성화한다.
- **근거**: 예약좌석(ReservationSeat)이 좌석을 참조하므로, 삭제하면 과거 예매 이력이 깨진다. D-05와 같은 원칙이다.
- **검토한 대안**: 좌석 물리 삭제 후 재생성 — 기존 예매 이력과의 연결이 끊김.
- **추후 확장**: 비활성화 일자 · 사유 등 이력 데이터는 현재 범위에서 제외.

### D-23. 좌석 위치 중복은 서비스 검증 + DB 유니크 제약으로 이중 방어

- **결정**: (screen_id, seat_row, seat_column)에 유니크 제약을 두고, 서비스에서도 저장 · 수정 전에 중복을 검사한다. 수정 시 중복 검사는 **엔티티를 변경하기 전에, 요청받은 새 위치 기준으로** 수행한다.
- **근거**: 서비스 검증만으로는 동시 요청을 막을 수 없어 DB 제약이 최종 방어선이 된다. 반대로 DB 제약만 있으면 사용자에게 500 오류가 나간다. 엔티티를 먼저 변경하면 중복 검사 쿼리 직전의 자동 flush가 UPDATE를 실행해 유니크 제약 위반(500)이 서비스 검증보다 먼저 발생한다.
- **검토한 대안**: 엔티티 변경 후 검사 — 자동 flush로 인해 위 문제가 실제로 발생함(2026-10-07 수정). 현재 위치 기준 검사 — 검사 대상이 자기 자신이 되어 중복을 걸러내지 못함.
- **관련**: 행 코드 변환 · 검증을 `Seat.toRowNum()`으로 분리해 엔티티와 서비스가 같은 규칙을 사용한다.

### D-24. 좌석 URL은 상영관 하위 중첩, 단건 조회 · 수정은 소속 검증

- **결정**: 모든 좌석 API를 `/api/screens/{screenId}/seats` 아래에 둔다. screenId는 경로에서만 받고 요청 DTO에는 넣지 않는다. 단건 조회 · 수정은 서비스에서 좌석의 상영관이 경로의 screenId와 일치하는지 검증하고, 다르면 거부한다. 수정 시 상영관 변경은 허용하지 않는다.
- **근거**: 좌석은 상영관에 종속된 자원이며, URL 구조를 일관되게 유지한다. 같은 값이 경로와 본문 두 곳에서 들어오면 서로 다를 때 어느 쪽을 따를지 모호해지므로 출처를 하나로 정한다. 소속 검증이 없으면 경로와 실제 좌석이 다른 상영관을 가리켜도 처리된다.
- **검토한 대안**: 단건 조회 · 수정만 `/api/seats/{seatId}`로 분리 — 값의 출처는 하나가 되지만 URL 일관성이 떨어짐.

### D-25. 좌석 API는 관리용, 고객용 좌석 조회는 별도 API

- **결정**: 좌석 조회는 STAFF 이상, 등록 · 수정은 MANAGER 이상으로 제한한다. 고객이 보는 좌석 배치도는 3단계에서 상영 일정 기준 API로 따로 만든다. 상영관 단건 조회(`GET /api/screens/*`)도 STAFF 이상으로 맞춘다.
- **근거**: 고객에게는 상영 일정별 예약 가능 여부가 필요하므로 좌석 설정 정보와 성격이 다르다. 좌석 상태 같은 운영 정보를 고객에게 노출하지 않는다.
- **주의**: `anyRequest().authenticated()` 구조상 규칙이 없는 새 API는 로그인한 모든 사용자에게 열린다(상영관 단건 조회에서 실제로 발견됨). → 2026-10-15 기본 거부(`denyAll`)로 전환해 구조적으로 해결(D-34).

### D-26. seatStatus는 생성 시 선택, 수정 시 필수

- **결정**: 좌석 생성 요청에 seatStatus가 없으면 기본값 ACTIVE를 유지하고, 수정 요청에서는 반드시 받는다. 엔티티의 `updateSeatStatus()`는 하나로 두고, 선택 여부는 서비스에서 표현한다.
- **근거**: 생성 시에는 대부분 활성 상태로 만들고, 수정 시에는 값이 명시돼야 변경 이력을 추적하기 쉽다.
- **검토한 대안**: 생성 요청에서 seatStatus를 받지 않고 항상 ACTIVE로 생성 — 더 단순하지만, 상태를 지정해 생성하는 경로가 사라짐.

### D-27. 좌석 등급은 상태로 관리, 비활성 등급은 새로 지정할 수 없음

- **결정**: 좌석 등급은 삭제하지 않고 `SeatGradeStatus`(ACTIVE / DEACTIVATED)로 관리한다. 비활성 등급은 좌석 등록 시 지정할 수 없고, 좌석 수정 시에는 **현재 등급과 다른** 비활성 등급으로 바꾸는 경우만 거부한다. 사용 중인 등급의 비활성화는 막지 않는다.
- **근거**: 좌석이 등급을 참조하므로 삭제하면 참조가 깨진다(D-22와 같은 원칙). 이미 그 등급을 쓰는 좌석은 그대로 운영하고 새 지정만 막는 것이 운영상 자연스럽다. 현재 등급을 유지하는 수정까지 막으면, 비활성 등급을 쓰는 좌석은 상태 변경 같은 다른 수정도 할 수 없게 된다.
- **검토한 대안**: 사용 중인 등급의 비활성화 금지 — 등급 정리를 하려면 모든 좌석을 먼저 옮겨야 해서 운영 부담이 큼.
- **구현 메모**: "같은 등급 유지" 판단은 상태가 아니라 id로 비교한다. 상태로 비교하면 서로 다른 비활성 등급 간 변경이 통과한다(2026-10-12 수정). 활성 여부는 엔티티의 인스턴스 메서드 `isActive()`로 판단한다.

### D-28. 좌석 등급명은 중복 금지, 가격은 0원 허용

- **결정**: 등급명은 trim한 값 기준으로 중복을 금지한다(서비스 검증 + DB 유니크 제약, 수정 시 검사 방식은 D-23과 동일). 같은 성격의 등급이 여럿 필요하면 "VIP-A", "VIP-B"처럼 구분한다. 기준 가격은 음수를 금지하고 0원(무료)은 허용한다. 요청 DTO에서 가격은 `Integer`로 받아 누락(null)을 거부한다.
- **근거**: `int`로 받으면 값이 누락돼도 0이 들어가고, 0원이 허용값이라 의도하지 않은 무료 등급이 조용히 만들어질 수 있다.
- **참고**: MySQL 기본 정렬 규칙은 대소문자를 구분하지 않아 "VIP"와 "vip"는 같은 이름으로 취급된다. 서비스 검증과 DB 제약이 같은 기준이라 일관성 문제는 없다.

## 8. 상영 일정(Showtime)

### D-29. 종료 시각은 영화 상영시간으로 계산해 저장

- **결정**: Movie에 상영시간(`runningTime`, 분)을 추가한다. 개봉 예정작은 미정일 수 있어 null을 허용하고, 값이 있으면 1 이상만 허용한다. 상영 일정의 종료 시각은 `Showtime.calcEndTime(시작, 영화)`로 계산해 **저장**하며, 외부에서 직접 설정할 수 없다. 상영시간이 없는 영화는 상영 일정을 만들 수 없다.
- **근거**: 겹침 검사를 DB 쿼리로 하려면 종료 시각 컬럼이 필요하다. 또한 영화 상영시간이 나중에 수정돼도 이미 편성된 일정의 종료 시각이 바뀌면 안 된다(D-08과 같은 발상).
- **검토한 대안**: 종료 시각을 저장하지 않고 조회 때마다 계산 — 겹침 쿼리가 복잡해지고, 상영시간 수정이 기존 일정에 소급됨.
- **구현 메모**: `calcEndTime()`은 엔티티 생성 전(등록 시 겹침 검사)에도 호출해야 하므로 static이며, 입력(시작 시각, 영화, 상영시간)의 null 검사를 스스로 한다.

### D-30. 같은 상영관의 상영 시간 겹침 검사

- **결정**: 같은 상영관에서 `기존.시작 < 새.종료 AND 기존.종료 > 새.시작`이면 겹침으로 판정해 거부한다. 끝나는 시각과 시작 시각이 같으면 겹치지 않는다. 비활성 일정도 시간대를 차지하는 것으로 보고 검사에 포함하며, 수정 시에는 자기 자신을 제외한다. 검사는 서비스에서 **엔티티 생성·변경 전에** 수행한다.
- **근거**: "겹치지 않음 = 기존이 새 시작 전에 끝남 OR 새 종료 후에 시작함"을 드 모르간 법칙으로 뒤집은 조건이다. 두 조건은 같은 행에서 동시에 성립해야 하므로 하나의 쿼리 메서드로 표현한다. 다른 행을 조회해야 하는 규칙이라 엔티티가 아닌 서비스가 담당한다(엔티티는 Spring Bean이 아니라 리포지토리를 주입받을 수 없음).
- **구현 메모**: 
  - Spring Data 파생 쿼리는 파라미터를 이름이 아닌 **순서**로 연결한다. `StartTimeLessThan`에는 새 종료, `EndTimeGreaterThan`에는 새 시작이 들어간다(2026-10-14 인자 순서 버그 수정).
  - 결과가 여러 건일 수 있어 `find`가 아닌 `exists`를 사용한다.
  - 등록용과 수정용(`IdNot`) 메서드를 분리한다. 등록 시 id는 null이고 SQL의 `id <> null`은 UNKNOWN이라 어떤 행도 찾지 못하기 때문이다.
- **한계**: 관리자 두 명이 동시에 같은 시간대를 등록하면 둘 다 통과할 수 있다. 시간 겹침은 유니크 제약으로 막을 수 없는 중복이며, 빈도가 낮아 현재는 허용한다. 3단계 동시성 작업에서 함께 검토한다.

### D-31. 상영 사이 여유 시간은 겹침 검사에만 반영

- **결정**: 청소·입장을 위한 여유 시간은 저장되는 종료 시각에 포함하지 않고, 겹침 검사 시 새 종료에 더하고 새 시작에서 빼서 반영한다. 값은 `application.properties`의 `cinema.showtime.buffer-minutes`로 관리한다.
- **근거**: 종료 시각에 포함하면 고객에게 보이는 종료 시각이 실제와 달라진다. 여유 시간은 등록·수정 시점에만 쓰이므로, 값을 바꿔도 기존 일정에는 영향이 없다.
- **검토한 대안**: 운영 설정 테이블 + 관리자 API(관리자가 런타임에 변경 가능, 구현량 큼), 상영관별 여유 시간 필드. 애플리케이션 전역 단일 인스턴스(Bean)에 값을 두는 방식은 재시작 시 값이 사라지고 다중 서버에서 일관되지 않아 제외.
- **확장 (우선순위 높음)**: 관리자가 API로 여유 시간을 변경하는 운영 설정 기능.

### D-32. 상영관·영화는 생성 후 변경 불가, 공개 여부는 활성화 시점에 검사

- **결정**: 상영 일정의 상영관과 영화는 생성자로만 받고 변경할 수 없다. 바꿔야 하면 새 일정을 만든다. 등록 시 상영관이 ACTIVE가 아니거나 영화가 상영 종료(ENDED)면 거부하고, 상영 예정(UPCOMING)은 허용한다. 영화의 노출(공개) 여부는 등록 시가 아니라 **일정을 ACTIVE(예매 오픈)로 바꿀 때** 검사한다. 상태는 `ShowtimeStatus`(ACTIVE / DEACTIVATED, 기본 DEACTIVATED) enum으로 관리한다.
- **근거**: 3단계에서 예약이 생기면 예약 좌석은 그 상영관의 좌석이므로, 상영관이 바뀌면 예약이 깨진다. 등록 시 노출 여부를 막으면 일정을 편성하기 위해 영화를 먼저 공개해야 해서, 일정 없는 영화가 고객에게 노출된다.
- **검토한 대안**: 노출 비활성 영화의 일정 등록 금지 — 위 운영 흐름 문제로 제외(2026-10-14 변경).

### D-33. 상영 일정의 시간 변경과 상태 변경 분리

- **결정**: 시간 변경은 `PUT /api/showtimes/{id}`(startTime), 상태 변경은 `PATCH /api/showtimes/{id}/status`(showtimeStatus)로 분리하고 요청 DTO도 나눈다. ACTIVE(예매 오픈)로 바꿀 때는 영화 공개, 영화 상영 종료 여부, 상영관 활성, 시작 전 여부를 검사하고, DEACTIVATED는 조건 없이 허용한다. 검사는 엔티티의 `updateShowtimeStatus()`에서 하며, 문자열을 enum으로 변환 → 검사 → 대입 순서를 지킨다.
- **근거**: 두 기능의 검증 규칙이 충돌한다. 하나의 PUT으로 합치면 상태만 바꿀 때도 startTime을 함께 보내야 하고, 이미 시작한 상영은 "과거 시각 금지"에 걸려 **예매를 닫을 수 없게** 된다. 상태 검사는 엔티티 자신의 정보(영화·상영관·시작 시각)만으로 판단할 수 있어 엔티티에 둔다.
- **구현 메모**: 영화 공개 검사는 `!= ACTIVE`(허용 목록) 방식으로 한다. `== DEACTIVATED`(차단 목록)로 쓰면 나중에 노출 상태 값이 늘어날 때 새 값이 검사를 통과한다.
- **검토한 대안**: Screen · SeatGrade처럼 PUT 하나로 처리 — 그쪽은 상태 변경에 별도 업무 규칙이 없어 충돌이 없었다. 규칙이 충돌하거나 성격이 다를 때만 분리한다.
- **확장**: 대관처럼 "고객에게 보이지만 예매는 불가"인 일정은 ACTIVE가 아닌 별도 상태(예: PRIVATE)로 추가한다. 시작 시각이 지난 일정의 활성화는 허용하지 않는다.

## 9. 보안 · 예외 처리

### D-34. 권한 규칙은 기본 거부(denyAll), 같은 권한끼리 묶음

- **결정**: SecurityConfig의 마지막 규칙을 `anyRequest().denyAll()`로 바꿔, 명시적으로 허용한 경로만 접근할 수 있게 한다. 규칙은 "HTTP 메서드 + 권한"이 같은 경로끼리 묶고, 좁은 경로를 넓은 경로보다 위에 둔다(처음 맞는 규칙이 적용됨). `/error`는 메서드 구분 없이 허용한다. 회원 전체 목록(`GET /api/members`)은 ADMIN 전용으로 한다.
- **근거**: 기존 `authenticated()` 구조에서는 규칙을 빠뜨린 API가 로그인한 모든 사용자에게 열렸고, 실제로 상영관 단건 조회와 **회원 전체 목록**이 그렇게 열려 있었다. 기본 거부면 규칙을 빠뜨린 API는 403이 되어 "안전한 쪽으로" 실패한다. `/error`가 막히면 실제 오류 대신 401/403이 보여 원인 파악이 어려워진다.
- **구현 메모**: 
  - `GET /api/members/myinfo`(CUSTOMER)는 `GET /api/members/*`(STAFF)보다 위에 있어야 한다.
  - 회원 PATCH는 `/api/members/**` 대신 실제 경로(`/*/nickname`, `/*/withdraw`)만 연다.
  - 존재하지 않는 경로도 규칙이 없으므로 403이 된다(경로 존재 여부를 노출하지 않음).
- **검증 (2026-10-15)**: 권한 경계마다 "기준 바로 아래 역할 403 / 기준 역할 성공"을 Postman으로 확인했다. 리뷰 중 회원 일괄 수정(PUT `/api/members/*`)이 MANAGER로 잘못 작성된 것을 발견해 ADMIN으로 바로잡았다(MANAGER가 자기 role을 ADMIN으로 바꿀 수 있는 권한 상승 구멍).

### D-35. 입력 오류는 400, 권한 위반은 403으로 처리

- **결정**: `GlobalExceptionHandler`에 다음 처리기를 둔다. 요청 본문 파싱 실패(`HttpMessageNotReadableException`), 필수 파라미터 누락(`MissingServletRequestParameterException`), 파라미터 타입 불일치(`MethodArgumentTypeMismatchException`)는 400, 서비스의 소유권 위반(`org.springframework.security.access.AccessDeniedException`)은 403. 응답에는 예외 클래스명이나 스택을 노출하지 않는다.
- **근거**: `@ExceptionHandler(Exception.class)`가 모든 예외를 잡기 때문에, Spring이 원래 400이나 403으로 처리하던 예외까지 500이 되고 있었다. 권한 위반을 400(IllegalArgumentException)으로 바꾸면 클라이언트가 "입력이 잘못됐다"고 오해하므로 403을 유지한다.
- **주의**: `AccessDeniedException`은 `java.nio.file` 패키지에도 같은 이름의 클래스가 있다. IDE 자동 import 시 Spring Security 쪽인지 확인한다.
- **보완 (2026-10-20)**: `ScreenService.updateScreen()`이 `Screen.ActiveStatus.valueOf(status)`를 그대로 호출해, 상태가 null이면 `NullPointerException`으로 500이 되고 잘못된 값이면 Java 기본 메시지가 노출되던 문제를 수정했다. `Screen.updateActiveStatus()`가 String을 받아 null·공백 검사 후 `valueOf`만 try/catch로 감싸 400으로 응답한다. String으로 상태값을 받는 다른 엔티티(Movie, Seat, SeatGrade, Showtime)와 같은 방식이다.
- **보완 예정 (2026-10-22 결정, 3단계 구현)**: DB 제약 위반(`DataIntegrityViolationException`)은 현재 500이 된다. 처리기를 추가해 **409 Conflict**("이미 존재하는 데이터와 충돌합니다")로 응답한다. 요청 형식은 올바르지만 현재 상태와 충돌한다는 의미라 400보다 정확하다. 예약 좌석 유니크 제약(D-40)뿐 아니라, 서비스 검사를 동시에 통과한 좌석 코드 · 등급명 중복에도 적용된다.
- **구현 (2026-10-25, 상태 충돌)**: `global.exception.ConflictException`(`RuntimeException` 상속)을 추가하고, `GlobalExceptionHandler`는 이 예외만 409로 응답한다. 10/23에 커밋했던 `IllegalStateException` → 409 처리기는 삭제했다.
  - 이유: `IllegalStateException`은 Spring · Hibernate · Java 라이브러리도 내부 오류에 쓰므로, 이를 409로 받으면 진짜 서버 버그가 로그 없이 "충돌"로 숨겨지고 내부 메시지가 노출된다. 이제 라이브러리의 `IllegalStateException`은 `Exception` 처리기(500 + `log.error`)로 간다.
  - `RuntimeException`을 상속한 이유: 체크 예외는 모든 호출 경로에 `throws`가 퍼지고, `@Transactional`은 기본적으로 언체크 예외에서만 롤백하므로 체크 예외로 만들면 충돌이 나도 변경이 커밋된다(D-42의 전체 롤백이 깨짐). `IllegalStateException`을 상속하지 않은 이유는 다른 곳에서 `IllegalStateException`을 잡을 때 함께 잡혀 분리 목적이 흐려지기 때문이다.
  - `ConflictException`의 메시지는 직접 쓴 한국어 문장이라 응답에 노출해도 D-35 원칙에 어긋나지 않는다. 예외는 "충돌"이라는 의미만 가지고 HTTP 변환은 처리기가 맡아, 엔티티가 웹 계층을 알지 않는다.
  - "이미 예약된 좌석"(D-39), "예약이 있는 상영 일정의 변경"(D-44)도 이 예외를 쓴다. DB 제약 위반(`DataIntegrityViolationException`) → 409는 유니크 제약이 생기는 예약 좌석 작업 이후 추가한다.
  - `IllegalArgumentException` → 400 처리기에도 라이브러리 예외를 그대로 노출하는 같은 위험이 있다. 우리 코드의 사용처가 수십 곳이라, 보류 항목인 예외 체계 정비(입력 오류 400 · 리소스 없음 404 전용 예외 도입) 때 함께 교체한다. `ConflictException`이 그 본보기다.

## 10. 테스트

### D-36. 통합 테스트 DB는 Testcontainers(MySQL)로 구성

- **결정**: 통합 테스트는 Testcontainers로 Docker 컨테이너에 실제 MySQL을 띄워 실행한다. MySQL 버전은 개발 DB와 같은 8.0으로 맞춘다. 개발 DB(`cinema`)에는 테스트가 접속하지 않게 한다.
- **근거**: 
  - 기존 `contextLoads` 테스트는 개발 DB에 접속해 통과하고 있었다. 테스트가 개발 데이터를 바꾸거나 개발 데이터 상태에 따라 결과가 달라질 수 있다.
  - H2(인메모리 DB)는 MySQL과 동작이 다르다. 예를 들어 등급명 중복 검사(D-28)는 MySQL의 대소문자 무시 정렬 규칙에 의존한다. 테스트는 통과했는데 실제 DB에서는 다르게 동작할 수 있다.
  - 같은 MySQL 안에 테스트용 스키마를 따로 두는 방식은 로컬 MySQL이 있어야 하고, CI 환경에서도 따로 준비해야 한다. Testcontainers는 Docker만 있으면 로컬과 CI(GitHub Actions)에서 같은 환경을 만든다.
  - 채용공고에서 자주 요구하는 Docker를 실제로 써 보는 기회가 된다.
- **검토한 대안**: H2 인메모리 DB, 로컬 MySQL의 별도 테스트 스키마.
- **준비 (2026-10-16)**: Docker Desktop(WSL2) 설치, `hello-world` 실행 확인, `mysql:8.0` 이미지 미리 받음.
- **구현 메모 (2026-10-19)**: 
  - 테스트 의존성: `spring-boot-testcontainers`, `org.testcontainers:testcontainers-junit-jupiter`, `org.testcontainers:testcontainers-mysql`. Testcontainers 2.0부터 모듈 이름에 `testcontainers-` 접두사가 붙고, `MySQLContainer` 패키지가 `org.testcontainers.mysql`로 바뀌었다. 버전은 Spring Boot가 관리하므로 적지 않는다.
  - 컨테이너는 `@TestConfiguration`의 `@Bean` + `@ServiceConnection`으로 선언하고, 테스트 클래스에서 `@Import`로 불러온다. 테스트 클래스의 `static @Container` 필드 방식은 클래스가 끝날 때마다 컨테이너를 멈춰 Spring 테스트 컨텍스트 캐시와 어긋날 수 있어 쓰지 않는다.
  - `@ServiceConnection`의 접속 정보가 `spring.datasource.*`보다 우선하므로 `application.properties`는 바꾸지 않는다. 테스트용 접속 정보를 어디에도 값으로 적지 않는다.
- **검증 (2026-10-19)**: `contextLoads`가 3306이 아닌 무작위 포트와 `test` DB로 접속해 통과했다.
- **남은 과제**: GitHub Actions에는 `CINEMA_JWT_SECRET` 등 환경변수가 없으므로 CI 구성 시 처리한다.

### D-37. 통합 테스트 작성 규칙

- **결정**: 서비스 단위 통합 테스트는 다음 규칙으로 작성한다.
  1. 클래스에 `@Import(TestcontainersConfiguration.class)` + `@SpringBootTest` + `@Transactional`을 붙인다. `@Transactional`은 테스트마다 DB 변경을 롤백해 테스트끼리 영향을 주지 않게 한다.
  2. 테스트 데이터는 리포지토리나 `new`가 아니라 **실제 서비스 메서드**로 만든다. 운영과 같은 검증을 거친 데이터로 테스트하기 위해서다.
  3. 날짜는 먼 미래(2099년)를 쓴다. 엔티티가 `LocalDateTime.now()`로 과거 시각을 거부하기 때문이다. Clock 주입은 필요해질 때 검토한다.
  4. 테스트 메서드 하나는 시나리오 하나만 검증하고, 의도는 한국어 `@DisplayName`으로 드러낸다.
  5. 거부 검증은 `assertThatThrownBy` + `isInstanceOf` + `hasMessageContaining`으로 **예외 종류와 거부 이유(메시지)**까지 확인한다. 같은 예외라도 다른 이유로 거부되면 의도한 검증이 아니기 때문이다.
  6. 성공 검증은 예외가 없는 것만 보지 않고 반환된 값(바뀐 상태, 시각 등)까지 확인한다.
  7. 새 테스트는 기대값을 일부러 바꿔 **실패하는 것을 한 번 확인**한다. 항상 통과하는 테스트는 검증하지 않는 테스트일 수 있다.
  8. 예외 메시지를 로그로 출력하지 않는다. 판정은 assertion이 하고, 실패 시에는 AssertJ가 실제 값을 보여준다.
  9. **(2026-10-23 추가) 단위 테스트**: 객체 하나 안에서 끝나는 규칙(예: 예약 상태 전이)은 Spring · DB 없이 단위 테스트로 검증한다. 테스트 대상이 쓰지 않는 협력 객체가 생성자 제약(`protected` 등)으로 만들기 어려우면 Mockito `mock()`으로 대신한다. 테스트할 상태는 필드를 직접 바꾸지 않고 public 메서드를 호출해 만든다. 거부 시에는 예외 · 메시지와 함께 **상태가 바뀌지 않았는지**도 확인한다.
- **근거**: 
  - `Movie`·`Screen`은 기본 생성자가 `protected`라 다른 패키지의 테스트에서 직접 만들 수 없다. 필수값 생성자를 추가하는 대신(보류 항목) 서비스로 만드는 방식을 택했고, 이것이 실제 생성 흐름(상영관 생성 → 상태 변경 등)을 그대로 검증하는 이점도 있다.
  - AI 초안 테스트는 개발자가 작성한 체크리스트로 리뷰한다. AI가 테스트를 통과시키려고 기대값이나 운영 코드를 바꾸지 않도록, 실패 시에는 고치지 말고 보고하게 한다.
- **적용 (2026-10-20)**: 
  - `ShowtimeOverlapTest` 7개 [직접 구현]: 경계값(10:45 허용 / 10:46 거부, 15:15 허용 / 15:14 거부), 완전 겹침, 다른 상영관, 수정 시 자기 자신 제외(D-30).
  - `SeatRegressionTest` 8개, `SeatGradeRegressionTest` 4개 [AI 초안]: 좌석 코드 중복, 자동 flush 버그, 소문자 행 코드 변환 순서, 비활성 등급(D-27), 등급명 trim·대소문자 중복(D-28).
  - 대소문자만 다른 등급명이 중복으로 거부되는 테스트(D-28)는 Java 코드가 아니라 MySQL 정렬 규칙에 의존한다. 컨테이너 DB에서 통과한 것으로 D-36의 판단(H2 대신 실제 MySQL)을 확인했다.


## 11. CI

### D-38. CI(GitHub Actions)는 통합 테스트까지 실행, 민감 정보는 Repository secret으로 전달

- **결정**: 
  - GitHub Actions는 push 시 `gradlew test`로 **모든 테스트**를 실행한다. 로드맵의 "CI 1단계는 단위 테스트, 통합 테스트는 3단계"를 앞당겨, Testcontainers 통합 테스트를 2단계부터 CI에 포함한다.
  - `CINEMA_JWT_SECRET`은 GitHub 레포의 **Repository secret**으로 등록하고 workflow에서 환경변수로 넘긴다. CI용 값은 로컬 값과 다른, 새로 만든 무작위 값(64바이트, Base64)을 쓴다.
- **근거**: 
  - 현재 테스트 20개가 모두 통합 테스트라, 계획대로 단위 테스트만 돌리면 CI에서 실행할 테스트가 없다. GitHub Actions의 `ubuntu-latest` runner에는 Docker가 있어 Testcontainers를 그대로 쓸 수 있다.
  - `gradlew test`는 종류와 관계없이 `src/test`의 테스트를 모두 실행하므로, 이후 단위 테스트가 추가돼도 설정을 바꿀 필요가 없다.
  - runner는 매번 새로 만들어지는 서버라 로컬 Windows 환경변수가 없다. 테스트 전용 설정 파일에 가짜 값을 적는 방식(검토한 대안)은 레포에 값이 남아 D-03 · CLAUDE.md 보안 규칙과 충돌할 소지가 있다.
  - Environment secret은 배포 환경별 값 분리와 승인 규칙용이라, 테스트만 하는 CI에는 Repository secret이 맞다. 배포(CD)를 붙일 때 다시 검토한다.
- **검토한 대안**: 단위 테스트만 CI에서 실행(로드맵 원안), `src/test/resources` 테스트 설정 파일에 가짜 secret 기재.
- **준비 (2026-10-21)**: 백엔드 레포에 Repository secret `CINEMA_JWT_SECRET` 등록. `CINEMA_DB_PASSWORD`는 `@ServiceConnection`이 접속 정보를 덮어쓰므로 등록하지 않고, 첫 실행 결과를 보고 판단한다.
- **구현 (2026-10-22)**: `.github/workflows/ci.yml` — `main` push · PR 시 `actions/checkout` → `actions/setup-java`(Temurin 17) → `gradle/actions/setup-gradle` → `chmod +x gradlew` → `./gradlew build`(secret을 환경변수로 전달) → 실패 시 `actions/upload-artifact`로 테스트 리포트 업로드.
  - action 버전은 Node.js 20 지원 종료 경고를 해결하는 최소 버전으로 둔다: checkout · setup-java · setup-gradle `v5`, upload-artifact `v6`(v5는 Node 20 기본). 더 최신 메이저가 있어도 안정성 원칙에 따라 경고가 생길 때 올린다.
  - Gradle은 통과한 테스트의 출력을 콘솔에 보여주지 않아, `build.gradle`의 test 작업에 `testLogging { events 'passed', 'skipped', 'failed'; exceptionFormat = 'full' }`를 추가했다. CI 로그에서 테스트별 결과(`@DisplayName`)를 바로 확인할 수 있다.
- **검증 (2026-10-22)**: CI에서 테스트 20개 PASSED, `BUILD SUCCESSFUL`. `CINEMA_DB_PASSWORD` 없이 통과해 `@ServiceConnection`이 접속 정보를 덮어쓴다는 예상을 확인했다(등록 불필요).


## 12. 예약 · 동시성 (2026-10-22 결정, 3단계 구현 예정)

### D-39. 좌석 동시 예약은 비관적 락 + DB 유니크 제약으로 이중 방어

- **결정**: 
  - 1차 방어: 예약 생성 시 **상영 일정(Showtime) 행을 비관적 락**(`@Lock(PESSIMISTIC_WRITE)`, `SELECT ... FOR UPDATE`)으로 잠근 뒤, 같은 상영 일정 · 좌석에 활성 예약(PENDING · CONFIRMED)이 있는지 **조인 조회**로 검사한다.
  - 2차 방어: `reservation_seats`의 `(상영 일정, 좌석, 활성 표시)` 유니크 제약(D-40).
- **근거**: 
  - "확인 후 저장"은 두 요청이 모두 확인을 마친 뒤 저장해 이중 예약이 생긴다(check-then-act 경합). `@Transactional`은 다른 트랜잭션의 동시 조회를 막지 않고, MySQL의 일반 `SELECT`는 잠그지 않는다.
  - 새 예약 행은 아직 없어서 잠글 수 없으므로, 이미 존재하는 상영 일정 행을 잠가 같은 상영 일정의 예약을 한 줄로 세운다. 한 건 처리 시간이 짧아 이 프로젝트 규모에서는 대기가 문제되지 않는다.
  - 인기 좌석처럼 충돌이 잦은 상황에서는 재시도가 반복되는 낙관적 락보다 유리하고, D-20(DB 락으로 시작)과 D-23(서비스 검사 + DB 제약 이중 방어) 패턴에 맞는다.
- **검토한 대안**: 비관적 락만(2차 방어 없음), 낙관적 락 + 상영 일정별 좌석 재고 테이블(구조 변경이 커서 Redis 고도화와 함께 확장 단계에서 검토).
- **참고**: 비관적 락에서도 늦게 온 요청은 거부된다. 사용자가 "고른 좌석을 빼앗기지 않는" 경험은 좌석 선점(PENDING, 7단계)이 만든다.

### D-40. 예약 좌석에 상영 일정 · 활성 표시를 반정규화하고, 동기화는 엔티티가 책임

- **결정**: 
  - `reservation_seats`에 상영 일정 컬럼과 활성 표시 컬럼(활성이면 1, 취소 · 만료면 NULL)을 추가하고 `(상영 일정, 좌석, 활성 표시)`에 유니크 제약을 건다.
  - 상영 일정 컬럼은 `ReservationSeat` 생성자에서 `reservation.getShowtime()`으로 채우고 변경 메서드를 두지 않는다.
  - 활성 표시 해제 메서드는 **package-private**으로 두어 `Reservation`의 `cancel()` · `expire()`를 통해서만 바뀌게 한다.
  - 이를 위해 `Reservation`에 `@OneToMany(mappedBy = "reservation")` 예약 좌석 목록(양방향 관계)과, 예약 좌석 생성 시 목록에도 함께 넣는 연관관계 편의 메서드를 둔다.
- **근거**: 
  - DB 유니크 제약은 **한 테이블의 컬럼만** 볼 수 있다. 상영 일정과 예약 상태는 `reservations`에만 있어 조인 조건으로는 제약을 걸 수 없으므로, 제약에 필요한 값을 `reservation_seats`에 둔다. 1차 서비스 검사(D-39)는 조인으로 충분하다.
  - MySQL은 조건부 인덱스(PostgreSQL의 partial index)를 지원하지 않는다. 대신 유니크 제약이 NULL끼리는 중복으로 보지 않는 점을 이용해, 취소 · 만료된 행은 몇 개든 공존하고 활성 행은 하나만 허용한다.
  - 취소 · 만료 시 행을 삭제하는 방식(검토한 대안)은 어떤 좌석의 예약이었는지 이력이 사라져 D-05 · D-22의 이력 보존 원칙과 충돌한다.
  - `mappedBy` 목록은 DB 컬럼을 만들지 않는 Java 쪽 역방향 조회다. 연관관계의 주인은 외래 키를 가진 `ReservationSeat`이며, 목록에만 넣어서는 저장되지 않는다. 같은 트랜잭션에서 새로 만든 예약의 목록은 자동 갱신되지 않으므로 편의 메서드로 양쪽을 함께 맞춘다.
- **비용**: 같은 정보가 두 곳에 있어 어긋날 위험이 있으며, 위 엔티티 설계로 막는다. 예매 내역 목록에서 예약별 좌석 목록에 접근하면 N+1이 생길 수 있다(4단계 대응 사례).
- **구현 (2026-10-26)**: 
  - `ReservationSeat`: 생성자는 package-private `(예약, 좌석, 가격)`이며 상영 일정을 `reservation.getShowtime()`으로 복사한다. 활성 표시는 `Boolean active`(컬럼 `active_flag`, NULL 허용)로 생성 시 `true`, `deactivate()`(package-private)에서 `null`로 바꾼다. **`false`를 쓰면 같은 좌석의 두 번째 취소가 유니크 제약에 걸리므로** 코드 주석에 변경 금지 경고를 남겼다. 컬럼 이름은 MySQL 키워드인 `ACTIVE`를 피해 `active_flag`로 했다. 유니크 제약 이름은 `uk_reservation_seats_showtime_seat_active`.
  - `Reservation`: `@OneToMany(mappedBy = "reservation")` 예약 좌석 목록, 예약 좌석은 `addSeat(좌석, 가격)`으로만 생성(결제 대기 상태에서만 허용, 생성 후 목록에 추가하고 반환). 목록은 `Collections.unmodifiableList`로 읽기 전용 반환해 편의 메서드 우회를 막는다. `cancel()` · `expire()`는 목록의 모든 좌석을 `deactivate()`한다.
  - 예약 좌석 생성 경로를 `addSeat()` 하나로 둔 이유: 서비스가 `new`로 만들고 생성자에서 예약 목록을 수정하는 방식(검토한 대안)은 흐름이 드러나지 않는다. `addSeat()`이 생성과 목록 추가를 함께 하므로 양쪽 관계가 어긋날 수 없고, 상태 검사도 한곳에서 한다.
  - **목록에 넣어도 DB에는 저장되지 않는다**(주인은 `ReservationSeat`). 서비스가 `addSeat()`이 돌려준 예약 좌석을 save해야 하며, 자동 저장(cascade)은 서비스 작업 때 검토한다.
  - DB: `ddl-auto=update`가 `showtime_id`(NOT NULL), `active_flag` 컬럼과 유니크 제약을 추가한 것을 `SHOW COLUMNS` · `SHOW INDEX`로 확인했다.
  - 검증: 단위 테스트 8개 추가(상영 일정 복사 · 초기 활성 · 가격 · 목록 포함, 취소 · 만료 시 해제, 확정 시 유지, 확정 후 좌석 추가 거부와 목록 불변, 좌석 null · 음수 가격 거부, 목록 직접 수정 거부). `false`로 바꾸면 해제 테스트가 실패하는 것을 확인했다. 전체 테스트 43개. NULL 유니크 기법이 실제 MySQL에서 동작하는지는 D-45의 2차 방어 검증(Testcontainers)에서 확인한다.

### D-41. 예약 상태는 사건별 메서드로만 변경, 3단계에서는 생성 즉시 확정

- **결정**: 
  - 범용 `updateReservationStatus()`를 없애고 public 메서드 `confirm()` · `cancel()` · `expire()`만 둔다. 출발 상태 검사는 private 메서드 하나로 모은다.
  - 전이 규칙: PENDING → CONFIRMED · CANCELED · EXPIRED, CONFIRMED → CANCELED. CANCELED · EXPIRED는 최종 상태로 어떤 변경도 거부한다.
  - `cancel()` · `expire()`는 상태 변경과 함께 예약 좌석의 활성 표시를 해제한다(D-40).
  - 3단계에서는 PG 결제가 없으므로 예약을 만들면 바로 CONFIRMED로 둔다. PENDING(좌석 선점) · EXPIRED(시간 초과)의 실제 사용은 7단계에서 시작한다.
- **근거**: 
  - 예약 상태는 외부 요청의 문자열이 아니라 결제 · 취소 · 만료라는 **사건의 결과**로 바뀐다. 문자열이 들어오지 않으므로 공백 · 형식 검사가 필요 없고, 상태를 직접 지정하는 공개 경로를 없애야 잘못된 전이를 호출할 방법 자체가 사라진다.
  - 관리자가 문자열로 상태를 바꾸는 기능이 생기면, 문자열 검사와 메서드 분기는 서비스 계층에서 한다.
  - PENDING 생성 + 임시 확정 API(검토한 대안)는 7단계에서 버릴 API가 생기고, 시간 초과 처리 없이 선점 좌석이 남는다.
- **보완 (2026-10-22)**: `reservationStatus`에 `@Enumerated(EnumType.STRING)`이 없어 순서 번호로 저장되던 문제를 수정했다. 상태를 중간에 추가하면 기존 데이터의 의미가 조용히 바뀌는 위험이 있었다. `ddl-auto=update`는 기존 컬럼 타입을 바꾸지 않아, 개발 DB의 숫자형 컬럼을 수동 삭제 후 재생성했다(예약 데이터 0건 확인).
- **구현 (2026-10-23)**: 
  - 각 메서드가 허용 출발 상태를 `EnumSet`으로 넘기고(`confirm` · `expire`: PENDING, `cancel`: PENDING · CONFIRMED), private `validateTransition(동작 이름, 허용 출발 상태)`이 현재 상태가 목록에 없으면 거부한다. **허용 목록 방식**이라 이후 상태(예: 환불)를 추가해도 허용 목록에 넣지 않는 한 자동으로 거부된다(D-33 · D-34와 같은 원칙). 처음 작성한 "PENDING이면 무엇이든 허용" 구조는 새 상태가 생기면 의도치 않은 전이가 열려 바꿨다.
  - `ReservationStatus`에 한국어 이름(label)을 두어 메시지 틀 하나("{상태} 상태의 예약은 {동작}할 수 없습니다.")로 모든 거부 사유를 안내한다. label은 DB에 저장되지 않는다(`EnumType.STRING`은 상수 이름을 저장).
  - 생성 시 기본값은 PENDING으로 두고, 3단계 서비스는 생성 직후 `confirm()`을 호출한다. 7단계에서는 호출 위치만 결제 승인 뒤로 옮긴다.
  - 검증: `ReservationTest` 단위 테스트 12개(메서드 3개 × 현재 상태 4개). 이 프로젝트의 첫 단위 테스트이며, 전체 테스트는 32개.

### D-42. 예약 가능 조건 · 좌석 수 · 금액 · 취소 정책

- **예약 거부 조건**: 
  1. 상영 일정이 DEACTIVATED
  2. 상영 시작 시각 이후 (허용 범위는 설정값으로 조정 가능하게 둠. 조회 가능 여부와는 별개 규칙)
  3. 좌석이 상영 일정의 상영관 소속이 아님 (D-24와 같은 취지)
  4. 좌석이 DEACTIVATED
  5. 이미 활성 예약(PENDING · CONFIRMED)이 있는 좌석. CANCELED · EXPIRED 좌석은 다시 예약 가능
  6. 한 요청 안에 같은 좌석이 중복됨
  7. 예약 대상 회원이 탈퇴함(`isWithdrawn`). 탈퇴 후에도 Access Token이 만료 전까지 유효하므로 서버에서 검사한다
- **거부하지 않는 조건**: 좌석 등급이 비활성인 좌석(D-27: 비활성은 새 지정만 막음). 가격은 그 등급의 기준 가격을 그대로 쓴다.
- **이메일 미인증 회원**: 예약 불가로 정했으나(로드맵 6단계 완료 조건), 인증 기능이 없는 지금 적용하면 모든 회원이 예약할 수 없으므로 6단계에서 추가한다.
- **좌석 수**: 예약 1건에 여러 좌석, 최대 8석(설정값). 일부 좌석이 실패하면 전체 롤백한다.
- **금액**: 좌석별 금액은 예약 시점의 등급 기준 가격을 `ReservationSeat.price`에 저장한다(D-08). 예약 총액은 저장하지 않고 좌석 금액의 합으로 계산해 응답한다. 총액 관리는 결제(7단계)의 몫이다.
- **취소**: 상영 시작 전까지(기준은 설정값). 삭제하지 않고 상태 변경 + 활성 표시 해제. 일부 좌석만 취소는 지원하지 않는다(부분 환불이 얽힘).
- **예매 변경**: 별도 기능을 두지 않고 취소 후 재예약. 기존 좌석 반환과 새 좌석 선점을 원자적으로 묶어야 해 동시성이 복잡해진다.
- **원칙**: 프론트엔드의 입력 방어는 사용자 편의이고, 최종 보장은 언제나 백엔드가 한다.

### D-43. 직원 예약: 회원 대리 예약 · 현장 판매, 예약의 주인과 처리 직원을 분리

- **결정**: 
  - STAFF 이상은 모든 회원의 예매를 조회 · 취소할 수 있다.
  - **회원 대리 예약**: STAFF가 대상 회원 id를 지정해 예약한다. 예약의 주인(`member`)은 대상 회원이다.
  - **현장 판매**: 예약의 주인은 **현장 판매 전용 시스템 계정**으로 한다. 직원은 자기 계정으로 로그인해 현장 판매를 요청한다.
  - `Reservation`에 `channel`(ONLINE / BOX_OFFICE)과 `handledBy`(처리 직원, 비어 있을 수 있음)를 추가한다.
  - `channel`은 요청 값이 아니라 **어떤 API로 들어왔는지**로 서버가 정한다. CUSTOMER용과 STAFF용 예약 API를 나누고(D-13과 같은 방식), CUSTOMER가 다른 회원 id를 지정하면 403으로 거부한다.
  - 시스템 계정은 앱 기동 시 없으면 생성하고(이메일은 설정값), 비밀번호는 아무도 모르는 무작위 값의 BCrypt 해시로 저장해 로그인할 수 없게 한다.
- **근거**: 
  - 근무 직원 계정으로 현장 판매를 기록하면 직원의 예매 내역이 판매 건으로 채워지고, 퇴사(탈퇴) 시 판매 예약이 탈퇴 회원 소유가 된다. 예약의 주인과 처리 직원이라는 다른 정보를 한 필드에 섞는 구조다.
  - 공유 판매 계정으로 로그인하는 방식은 누가 판매했는지 추적할 수 없고 계정 공유 자체가 보안상 바람직하지 않다.
  - 비회원용 Role 추가는 권한 체계로 데이터를 구분하는 것이다. D-12에서 비로그인 구분용 GUEST Role을 같은 이유로 채택하지 않았다.
  - `handledBy` 덕분에 회원 대리 예약에서도 처리 직원이 남는다. `channel`은 이후 관리자 통계에도 쓸 수 있다.
- **확장으로 둔 것**: 비회원 온라인 예매(휴대폰 번호 · 조회 비밀번호, 별도 인증 흐름 필요, 확장 중 우선순위 높음). 이때도 `channel` · `handledBy`는 그대로 쓴다.
- **후속 작업**: `Member.Role` 주석(STAFF의 "예매 등록 · 편집", CUSTOMER의 "편집(예매변경)")을 실제 동작에 맞게 수정한다.
- **구현 (2026-10-25)**: 
  - 생성자를 private으로 두고 **정적 팩토리 메서드** `Reservation.online(회원, 상영 일정)` · `Reservation.boxOffice(회원, 상영 일정, 처리 직원)`로만 생성한다. `online()`은 경로 ONLINE · 처리 직원 없음을 스스로 채우고, `boxOffice()`는 처리 직원이 null이면 거부한다(400). 호출하는 쪽이 null을 넘기거나 경로와 처리 직원을 잘못 조합할 방법이 없다. 생성자 하나에 인자 4개를 받는 안(검토한 대안)은 온라인 예약에 null을 넘겨야 하고 잘못된 조합을 생성자 검사에 의존한다.
  - `Channel` enum(ONLINE "온라인" / BOX_OFFICE "매표소"), `channel`(NOT NULL), `handledBy`(`handled_by_id`, NULL 허용) 추가. 둘 다 변경 메서드가 없다(D-10). 새 컬럼 추가는 `ddl-auto=update`가 처리했다.
  - 처리 직원이 STAFF 이상인지는 서비스에서 검사한다(권한 계층은 Spring Security가 관리).
  - `Member.Role` 주석을 수정했다: STAFF는 예매 등록(회원 대리 예약 · 현장 판매)과 전체 회원 예매 조회 · 취소, CUSTOMER는 자기 예매 등록 · 조회 · 취소. 예매 변경은 전 등급 공통으로 취소 후 재예약.
  - 검증: 단위 테스트에 생성 규칙 3개 추가(경로 · 처리 직원이 올바르게 채워지는지, 매표소 예약의 처리 직원 누락 거부). 전체 테스트 35개.

### D-44. 상영 일정 변경 제한과 등록 경합도 비관적 락으로 처리

- **결정**: 
  - 활성 예약이 있는 상영 일정은 **시간 변경과 비활성화를 거부**한다. 판단 전에 상영 일정 행을 잠가, 예약 생성과 일정 변경이 동시에 끼어들지 않게 한다.
  - 상영 일정 등록 · 시간 변경의 겹침 검사 전에는 **상영관(Screen) 행을 잠근다.** 범위 겹침은 유니크 제약으로 표현할 수 없고 MySQL에는 배제 제약(PostgreSQL의 exclusion constraint)이 없어 락 단일 방어로 한다.
  - 시간 변경은 상영 일정과 상영관을 모두 잠그므로, 교착 상태를 피하도록 **잠금 순서를 하나로 고정**한다(구현 시 결정).
- **근거**: 예약 후 시간이 바뀌면 고객은 모르는 사이 다른 시간의 표를 갖게 된다. 부득이한 변경은 프로그램 기능이 아니라 운영 절차(고객 안내 → 예약 취소 → 변경)의 문제다. 상영 일정 등록 경합은 드물고 관리자 간 소통으로도 막을 수 있어 2차 방어까지는 두지 않는다.
- **해결된 보류 항목**: 예약이 있는 상영 일정의 시간 변경 제한, 같은 상영관 상영 일정 동시 등록 경합(2026-10-14 등록).
- **확장으로 둔 것**: 상영 취소 시 예약 일괄 취소 · 환불(결제 이후).

### D-45. 동시성 테스트 규칙 (D-37의 예외)

- **결정**: 
  - 여러 회원이 `ExecutorService` 스레드에서 `CountDownLatch` 신호와 함께 같은 좌석을 예약하고, 성공 1건 · 실패 N-1건 · 활성 예약 좌석 1건을 검증한다.
  - 동시성 테스트는 별도 클래스로 두고 `@Transactional`을 붙이지 않는다. `@AfterEach`에서 테스트가 만든 데이터를 외래 키 순서대로 직접 삭제한다.
  - 테스트를 먼저 작성해 **락 없이 이중 예약이 생기는 것**을 확인한 뒤 락을 추가해 통과시킨다. 동시성 버그는 타이밍에 따라 재현되지 않을 수 있어 스레드 수를 충분히 두고 여러 번 실행한다.
  - 2차 방어도 따로 검증한다: 리포지토리로 같은 좌석의 활성 행 두 개 저장 시 DB가 거부하는지, 활성 표시 NULL 행은 여러 개 저장되는지.
- **근거**: 각 스레드는 자기 트랜잭션으로 실제 커밋해야 서로의 결과와 락을 본다. 테스트 클래스의 트랜잭션은 다른 스레드로 전달되지 않고, 준비 데이터가 커밋되지 않아 다른 스레드에서 보이지 않는다. 컨테이너 DB는 모든 테스트 클래스가 공유하므로 정리를 빠뜨리면 다른 테스트가 실패한다. 전체 TRUNCATE(검토한 대안)보다 지우는 범위가 명시적이다.
