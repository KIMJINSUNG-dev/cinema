## 1. 비관적 락을 걸었는데도 서비스 검사가 이중 예약을 잡지 못함 (2026-10-28)

관련 결정: D-39(동시성 이중 방어), D-40(예약 좌석 유니크 제약), D-45(동시성 테스트)

### 상황

같은 좌석에 회원 10명이 **동시에** 예약을 요청하는 테스트를 만들었습니다.
목표는 1명만 성공하고, 나머지 9명은 서비스 검사에서 "이미 예약된 좌석입니다"(**409**)로 거절되는 것입니다.

방어는 두 겹입니다.

- **1차 방어**: 서비스가 "이 좌석에 활성 예약이 있는지" 확인하고 있으면 409로 거절
- **2차 방어**: DB 유니크 제약 `(상영 일정, 좌석, 활성 표시)`. 1차가 놓쳐도 DB가 중복 저장을 거부

### 비유: 영화관 매표소

| 개념 | 비유 |
| --- | --- |
| DB의 예약 데이터 | 매표소의 **실제 좌석 현황판** |
| 서비스 검사 | 손님이 현황판을 보고 "이 좌석 비었나?" 확인 |
| DB 유니크 제약 | 직원이 마지막에 "이미 팔린 좌석이에요" 하고 거절 |
| 비관적 락 | 매표소 앞에 **한 줄로** 서게 함 |
| `REPEATABLE_READ` 스냅샷 | 건물에 들어올 때 현황판을 **사진**으로 찍어 두고 그 사진만 봄 (MySQL 기본 동작) |

### 단계별 실험 결과

| 단계 | 구성 | 결과 | 비유로 보면 |
| --- | --- | --- | --- |
| 1 | 검사 ✗, 락 ✗ | 성공 1, 실패 9 (모두 DB 오류) | 10명이 확인 없이 몰려감 → 직원이 9명 거절 |
| 2 | 검사 ○, 락 ✗ | 성공 1, 실패 9 (모두 DB 오류) | 10명이 **동시에** 현황판을 봄. 아직 아무도 안 샀으니 모두 "비었다" → 직원이 9명 거절 |
| 3 | 검사 ○, 락 ○ | 성공 1, 실패 9 (모두 DB 오류) | 한 줄로 섰지만(락은 정상 동작), 각자 **입장할 때 찍은 사진**을 보고 확인 → 모두 "비었다" → 직원이 9명 거절 |
| 4 | 검사 ○, 락 ○, `READ_COMMITTED` | **성공 1, 실패 9 (모두 409)** ✅ | 줄을 선 뒤 **실제 현황판**을 봄 → 앞사람이 산 좌석이 보여서 검사가 거절 |

- **모든 단계에서 이중 예약은 생기지 않았습니다.** 2차 방어(DB 유니크 제약)가 매번 막았습니다.
- 문제는 거절된 사용자가 받는 응답이었습니다. DB가 막으면 `DataIntegrityViolationException`이 발생하고, 처리기가 없어 **500(서버 오류)**이 됐습니다.

### 원인

MySQL의 기본 격리 수준 `REPEATABLE_READ`에서는 일반 SELECT가 **트랜잭션에서 처음 조회한 순간의 상태(스냅샷)**를 끝까지 봅니다.

```
나중에 온 요청의 트랜잭션:
  ① 회원 조회        ← 이때 스냅샷 생성 (먼저 온 요청은 아직 커밋 전)
  ② 상영 일정 락 요청 ← 대기 … 먼저 온 요청이 커밋 … 락 획득
  ③ 예약 좌석 검사    ← ①의 스냅샷으로 읽음 → 먼저 온 예약이 안 보임
  ④ 저장             ← DB 유니크 제약에 걸림
```

**락은 순서를 세워 줄 뿐, 일반 SELECT가 무엇을 보는지는 격리 수준이 정합니다.**

### 해결

예약 생성 메서드에만 격리 수준을 지정했습니다.

```java
// 락을 적용한 뒤 예약 좌석 검사 시 최신 커밋을 체크하도록 READ_COMMITTED 지정
@Transactional(isolation = Isolation.READ_COMMITTED)
public Long createOnlineReservation(...) {
    ...
    Showtime showtime = showtimeRepository.findByIdForUpdate(showtimeId) // 비관적 락
    ...
    if (reservationSeatRepository.existsByShowtimeIdAndSeatIdAndActiveTrue(showtimeId, seatId)) {
        throw new ConflictException(seat.getSeatCode() + " 좌석은 이미 예약된 좌석입니다.");
    }
    ...
}
```

`READ_COMMITTED`에서는 조회할 때마다 **그 순간까지 커밋된 최신 상태**를 봅니다.

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 락 조회를 메서드 맨 앞으로 이동 | 지금은 동작하지만, 나중에 락 앞에 조회를 하나만 추가해도 경고 없이 다시 깨짐 |
| 검사 쿼리도 잠금 읽기(`FOR UPDATE`)로 | 없는 행을 잠그면 갭 락이 생겨 교착 상태 위험 |
| 애플리케이션 전체를 `READ_COMMITTED`로 | 모든 기능에 영향을 주는 변경이라 범위가 너무 큼 |

추가로 `DataIntegrityViolationException` → **409** 처리기도 만들었습니다. 1차 방어가 놓치는 경우에도 사용자는 500이 아니라 409를 받습니다(D-35).

### 배운 점

- **비관적 락만으로는 부족할 수 있다.** 락(순서)과 격리 수준(무엇을 보는지)이 함께 맞아야 "확인 후 저장"이 안전하다.
- **테스트가 성공 건수만 봤다면 문제를 놓쳤다.** 1~3단계 모두 "성공 1건"이라 통과처럼 보였다. 실패한 예외의 **종류**까지 검증해서 1차 방어가 동작하지 않는다는 걸 발견했다.
- **DB 제약(2차 방어)은 실제로 데이터를 지켰다.** 1차 방어가 실패한 세 번 모두 이중 예약을 막았다. 이중 방어 설계(D-39)가 옳았음을 확인했다.
- 로그에서 쿼리 순서(검사 쿼리가 몰려 있는지, 한 명씩 진행되는지)를 보면 동시성 동작을 눈으로 확인할 수 있다.

## 2. 2차 방어가 없는 영역: 락이나 격리 수준 하나만 빠져도 겹치는 상영 일정이 저장됨 (2026-11-01)

관련 결정: D-44(상영 일정 등록 경합 · 변경 제한), D-39(좌석 예약 이중 방어와 비교)

### 상황

같은 상영관 · 같은 시간대의 상영 일정을 관리자 5명이 **동시에** 등록하는 테스트를 만들었습니다.
목표는 1건만 저장되고 나머지 4건은 "새 상영스케줄이 기존 상영스케줄과 겹칩니다"(400)로 거절되는 것입니다.

좌석 예약(1번 항목)과 다른 점이 하나 있습니다.
**"시간 범위가 겹치면 안 된다"는 규칙은 DB 유니크 제약으로 표현할 수 없습니다.**
유니크 제약은 "같은 값이 두 번 들어오면 안 된다"만 막을 수 있고, "13:00~15:00과 14:00~16:00이 겹친다" 같은 범위 비교는 하지 못합니다.
(PostgreSQL에는 이런 경우를 위한 배제 제약이 있지만 MySQL에는 없습니다.)
그래서 상영 일정 등록은 **상영관 락 + 격리 수준(1차 방어)만으로** 지켜집니다.

### 실험: 방어를 하나씩 빼 보기

`createShowtime()`의 코드를 잠시 바꿔 동시성 테스트를 실행하고, 끝나면 원래대로 되돌렸습니다(GitHub Desktop의 Discard changes).

| 구성 | 결과 | 비유(매표소) |
| --- | --- | --- |
| 락 ○, `READ_COMMITTED` ○ (현재 코드) | 성공 1, 거절 4 ✅ | 한 줄로 서서, 차례가 오면 실제 현황판을 봄 |
| 실험 1: 락 ✗, `READ_COMMITTED` ○ | **성공 5** ❌ | 5명이 동시에 현황판을 봄. 아무도 아직 등록 안 했으니 모두 "비었다" |
| 실험 2: 락 ○, `READ_COMMITTED` ✗ | **성공 5** ❌ | 한 줄로는 섰지만, 건물에 들어올 때 찍은 **사진**을 보고 판단 |

**"성공 5"는 같은 상영관 · 같은 시간에 상영 일정 5개가 실제로 저장됐다는 뜻입니다.**

실험 2가 실패한 이유: `createShowtime()`은 상영관을 잠그기 **전에** 영화를 조회합니다(일반 SELECT).
MySQL 기본 격리 수준(`REPEATABLE_READ`)에서는 이 첫 조회 순간에 스냅샷(사진)이 만들어지므로,
줄을 서서 기다린 뒤 겹침을 검사해도 앞사람이 저장한 상영 일정이 보이지 않습니다.

### 좌석 예약(1번 항목)과 비교

| | 좌석 예약 (10/28) | 상영 일정 등록 (11/01) |
| --- | --- | --- |
| 1차 방어(락 + 격리 수준)가 빠지면 | 9건이 DB 오류로 거절됨 (응답만 500) | **5건 모두 저장됨** |
| 이유 | DB 유니크 제약(2차 방어)이 마지막에 막음 | 범위 겹침은 유니크 제약으로 막을 수 없음 |
| 데이터 | 안전 | **망가짐** |

### 해결 (현재 코드)

- 겹침 검사 전에 상영관 행을 잠금: `ScreenRepository.findByIdForUpdate()`
- 등록 · 시간 변경 · 상태 변경 메서드에 `@Transactional(isolation = Isolation.READ_COMMITTED)`
- 이 조합을 지키는 동시성 테스트: `ShowtimeConcurrencyTest` (5개 동시 등록 → 1건만 성공)

### 배운 점

- **유니크 제약으로 표현할 수 없는 규칙은 락 + 격리 수준이 유일한 방어다.** 둘 중 하나만 빠져도 데이터가 실제로 망가진다.
- 그래서 **2차 방어가 없는 곳일수록 1차 방어를 지키는 동시성 테스트가 중요하다.** 누군가 락이나 격리 수준을 지우면 이 테스트가 바로 실패한다.
- 좌석 예약에서 이중 방어(D-39)를, 상영 일정에서 락 단일 방어(D-44)를 택한 차이가 실험 결과로 그대로 드러났다.
- 의도적 실패 실험은 GitHub Desktop의 Discard changes로 되돌리면 안전하고, 되돌린 뒤 전체 테스트를 한 번 더 돌려 원래 상태를 확인한다.

## 3. 영화 장르를 그대로 두고 수정하면 409: 지연된 DELETE와 즉시 실행된 INSERT의 충돌 (2026-11-03)

관련 결정: D-07(중간 엔티티, 장르 변경은 삭제 후 재생성), D-48(영화 동적 검색)

### 상황

영화 검색 테스트를 Claude Code에 맡겼는데(AI 초안), 테스트 데이터를 만드는 과정에서 Claude Code가 **기존 서비스의 버그**를 발견했습니다.
CLAUDE.md의 "기존 코드는 수정하지 말고 보고" 규칙에 따라 코드를 고치지 않고, 버그를 피해 테스트를 작성한 뒤 원인 추정과 함께 보고했습니다.

- 현상: `updateMovie()`에 **기존 장르와 하나라도 겹치는** `genreIds`를 넣으면 `movie_genres`의 `(movie_id, genre_id)` 유니크 제약 위반(`DataIntegrityViolationException` → 409)
- 예: [액션, SF] → [SF, 드라마]도 실패. 장르를 유지한 채 이름만 고치는 **가장 흔한 수정이 실패**하는 상태였습니다.
- 기존 테스트가 이 경로(겹치는 장르로 수정)를 다루지 않아 지금까지 드러나지 않았습니다.

### 비유: 예약석 명단

명단에서 이름을 지우겠다고 **메모만 해 두고**(삭제 지연), 같은 이름을 **곧바로 펜으로 다시 써 넣으려다가**(즉시 삽입) "이미 있는 이름"이라고 거절당한 상황입니다.

### 원인

```java
movieGenreRepository.deleteAll(movieGenreRepository.findByMovieId(id)); // DELETE는 대기
...
movieGenreRepository.save(new MovieGenre(movie, genre));                // INSERT는 즉시
```

- `deleteAll()`(내부적으로 `em.remove()`)은 DELETE를 바로 보내지 않고 **플러시 때까지 미룹니다.**
- `MovieGenre`의 id는 IDENTITY 전략이라, DB가 id를 만들어 줘야 하므로 `save()`가 **INSERT를 즉시** 실행합니다.
- 그래서 DB에는 아직 기존 `(영화, 장르)` 행이 남아 있는 상태에서 같은 행이 다시 들어와 유니크 제약에 걸립니다.

Claude Code의 첫 보고는 "플러시할 때 Hibernate가 삽입을 삭제보다 먼저 실행해서"였습니다. 방향은 맞지만, 이 프로젝트에서는 **IDENTITY의 즉시 INSERT**가 더 직접적인 원인이라 원인 설명을 이렇게 보정했습니다(10월에 정리한 "IDENTITY와 `save()`" 개념과 같은 원리).

### 해결

1. **재현 먼저**: Claude Code에 회귀 테스트 `MovieUpdateGenreTest` 5개를 맡겨, 수정 전 상태에서 실행했습니다.

   | 시나리오 | 수정 전 | 수정 후 |
   | --- | --- | --- |
   | [A, B] → [A, B] (동일) | ❌ `Duplicate entry` | ✅ |
   | [A, B] → [B, C] (일부 겹침) | ❌ `Duplicate entry` | ✅ |
   | [A] → [B] (전부 교체) | ✅ | ✅ |
   | [A, B] → null / 빈 리스트 | ✅ | ✅ |

   "겹치는 장르가 하나라도 있을 때만 실패한다"는 분석이 테스트로 증명됐습니다.
2. **수정** [직접 구현]: `deleteAll()` 직후 `movieGenreRepository.flush()`를 추가해 DELETE를 먼저 DB에 반영합니다. 플러시는 커밋이 아니므로 이후 예외가 나면 함께 롤백됩니다.
3. 검색 테스트에 남아 있던 "버그를 피해 가는" 주석과 회귀 테스트 주석을 현재 상태에 맞게 정리했습니다.

검토한 다른 방법: JPQL 일괄 삭제(`@Modifying`, 즉시 실행되지만 D-37 규칙 2 예외 승인과 영속성 컨텍스트 정리가 필요), 바뀐 장르만 추가 · 삭제(가장 효율적이지만 장르가 영화당 몇 개뿐이라 과함).

### 배운 점

- **JPA가 SQL을 "언제" 보내는지는 연산마다 다르다.** 삭제 · 수정은 플러시까지 미뤄지지만, IDENTITY 전략의 저장은 즉시 실행된다. "삭제 후 같은 값 재삽입" 코드는 유니크 제약이 있으면 이 차이에 걸린다.
- 회귀 테스트에서 `findByMovieId()` 같은 JPQL 조회는 실행 전에 자동 플러시(기본 모드 AUTO)가 일어나, 지연된 DELETE가 검증 시점에는 반영되어 있다. 그래서 "전부 삭제" 시나리오는 수정 전에도 통과했다.
- **AI 작업 규칙이 실제로 작동한 사례**: 범위 밖 코드를 고치지 않고 보고하게 한 덕분에 버그를 놓치지 않았고, 개발자가 원인을 검토 · 보정한 뒤 직접 수정할 수 있었다.
- 버그를 고칠 때는 **실패하는 테스트로 먼저 재현**하면, 수정이 실제로 효과가 있다는 증거가 남고 같은 버그의 재발도 막는다.
