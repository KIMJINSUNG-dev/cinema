# Cinema — 영화 예매 시스템 (백엔드)

상영관 · 좌석 · 상영 일정 관리부터 좌석 예약까지, 영화관 예매 서비스의 핵심 흐름을 구현하는 백엔드 프로젝트입니다.
**동시 예약 처리, 조회 성능(N+1), 테스트 · CI**처럼 실무에서 문제가 되는 지점을 직접 부딪쳐 보고, 결정과 그 근거를 문서로 남기는 것을 목표로 진행하고 있습니다.

> **진행 상황 (2026-11-08)**: 10단계 중 **4단계까지 완료** (예약 · 동시성, QueryDSL · N+1 대응).
> 다음은 5단계 사용자 화면 1차(프론트엔드)이며, 최소 완성본 목표는 2027-01-29입니다. → [개발 로드맵](docs/roadmap.md)

## 구현 기능

### 완료
- **회원 · 인증**: 회원가입, 로그인 · 로그아웃 · 토큰 재발급, 4단계 권한(CUSTOMER < STAFF < MANAGER < ADMIN)과 역할 계층, 본인 리소스 소유권 검증
- **상영관 · 좌석 · 좌석 등급**: 상영관별 좌석 배치, 좌석 등급별 기준 가격, 삭제 대신 상태로 관리(예약 이력 보존)
- **영화**: 장르(다대다를 중간 엔티티로), 상영 상태와 공개 여부를 별도 축으로 관리, **동적 검색**(제목 · 장르 · 상영 상태)
- **상영 일정**: 종료 시각 자동 계산, 같은 상영관의 시간 겹침 검사(상영 사이 여유 시간 포함), 예약이 있는 일정의 변경 · 비활성화 제한, **고객용 상영시간표**(날짜별, 예약 가능한 일정만)
- **예약**: 온라인 예매, 매표소 예약(회원 대리 예약 · 현장 판매), 1회 최대 좌석 수, 좌석 등급별 가격, 예매 내역 조회(고객용 · 직원용 분리), 상영 15분 전까지 취소
- **동시성**: 같은 좌석 동시 예약, 같은 상영관 동시 일정 등록에서 데이터 무결성 보장

### 예정
- 사용자 화면(조회 → 상영시간 선택 → 좌석 선택 → 예약), 고객용 좌석 배치도 API
- 이메일 인증 · 비밀번호 재발급 · 아이디 찾기
- PG 결제(샌드박스)와 좌석 선점(결제 대기 → 확정 · 만료)
- 관리자 화면

## 핵심 구현

### 1. 좌석 동시 예약: 비관적 락 + 격리 수준 + DB 유니크 제약 이중 방어
같은 좌석에 10명이 동시에 예약해도 **1명만 성공하고 9명은 409**를 받도록 설계했습니다.

- **1차 방어**: 예약 시 상영 일정 행을 `SELECT ... FOR UPDATE`(비관적 락)로 잠가 같은 상영 일정의 예약을 한 줄로 세우고, 이미 예약된 좌석인지 검사합니다.
- **격리 수준**: MySQL 기본 `REPEATABLE_READ`에서는 락을 기다린 뒤에도 트랜잭션 첫 조회 시점의 스냅샷을 봐서 앞사람의 예약이 보이지 않았습니다. 예약 생성 메서드만 `READ_COMMITTED`로 지정해 해결했습니다. **락은 순서를, 격리 수준은 무엇을 보는지를 정합니다.**
- **2차 방어**: `reservation_seats`의 `(상영 일정, 좌석, 활성 표시)` 유니크 제약. 취소된 예약끼리는 중복을 허용해야 해서, 비활성 상태를 `false`가 아니라 `NULL`로 저장하는 방식(MySQL은 NULL을 중복으로 보지 않음)을 썼습니다.
- 동시성 테스트로 검증했고, 락 · 검사 · 격리 수준을 하나씩 빼는 실험으로 각 방어의 역할을 확인했습니다. → [트러블슈팅 1](docs/troubleshooting.md)

### 2. 상영 일정 등록 경합: 유니크 제약으로 막을 수 없는 규칙
"시간 범위가 겹치면 안 된다"는 규칙은 DB 유니크 제약으로 표현할 수 없습니다. 그래서 상영관 행 락 + `READ_COMMITTED`가 **유일한 방어**입니다.
실험에서 락이나 격리 수준 중 하나만 빠져도 **겹치는 상영 일정 5건이 실제로 저장**되는 것을 확인했고, 이 조합을 동시성 테스트로 고정했습니다. → [트러블슈팅 2](docs/troubleshooting.md)

### 3. QueryDSL 동적 검색
조건 3개(제목 · 장르 · 상영 상태)의 조합 8가지를 메서드 이름 방식으로 만들 수 없어, 사용자 정의 리포지토리(`RepositoryCustom` + `Impl`)에서 QueryDSL로 구현했습니다.
- 값이 없는 조건은 `null`을 돌려 `where()`에서 무시되게 해 쿼리 하나로 처리
- 장르 조건은 JOIN 대신 **서브쿼리**로 걸러 페이지 크기 · 전체 개수가 어긋나지 않게 함
- 이 과정에서 검색어 없는 목록이 **비공개 영화까지 노출**하던 문제를 발견해, 목록과 검색을 공개 영화만 조회하는 API 하나로 통합

### 4. N+1 문제: 측정 → 원인 분석 → 관계별 해결
Hibernate 통계로 SQL 실행 수를 세는 테스트를 먼저 만들고(개선 전 수치 기록), 개선 후 수치를 고정해 재발을 막았습니다.

| 대상 | 개선 전 | 개선 후 | 방법 |
| --- | --- | --- | --- |
| 영화 목록 (영화 → 장르) | 14건 | **2건** | 영화 id `IN` 일괄 조회 + 장르 fetch join |
| 직원용 상영관별 상영 일정 (→ 영화) | 5건 | **2건** | 영화 fetch join |
| 고객용 상영시간표 (→ 영화 · 상영관) | — | **1건** | 처음부터 QueryDSL `fetchJoin()` |
| 예매 내역 목록 (→ 상영 일정 · 영화 · 상영관, → 예약 좌석 → 좌석) | 30건 | 20건 → **4건** | 다대일은 `@EntityGraph`, 일대다는 `default_batch_fetch_size` |

- 판단 기준은 **"JOIN하면 행이 불어나는가"** 입니다. 다대일은 페이징 쿼리에 함께 fetch join하고, 일대다는 페이징 쿼리와 분리해 `IN`으로 묶어 읽습니다.
- 같은 일대다라도 **엔티티에 컬렉션 필드가 있으면 배치 크기 설정, 없으면 직접 `IN` 조회**를 택했습니다(영화에는 장르 컬렉션이 없고, 예약에는 예약 좌석 컬렉션이 있음).
- `EXPLAIN`으로 일괄 조회 쿼리가 인덱스를 타는지(range · eq_ref) 확인했습니다.
- **OSIV를 껐습니다**(`spring.jpa.open-in-view=false`). 서비스가 트랜잭션 안에서 DTO로 변환하는 규칙을 설정으로 강제해, 서비스 밖에서 쿼리가 몰래 나가는 일을 막고 DB 연결 보유 시간을 줄였습니다.

### 5. 인증
- Access Token + Refresh Token(JWT). Refresh Token은 **HttpOnly 쿠키**로 전달해 스크립트에서 접근할 수 없게 함
- Redis에 `이메일 + 기기 ID` 단위로 Refresh Token을 저장해 **다중 기기 로그인** 지원
- 재발급 시 역할을 토큰이 아니라 **DB에서 다시 조회**해 권한 변경을 반영. 매표소 예약처럼 처리 직원이 기록으로 남는 작업은 요청마다 DB 기준으로 직원 권한을 재확인
- `SecurityConfig`는 **기본 거부(`denyAll`)** 구조로, 규칙을 빠뜨린 API가 열리지 않게 함

## 테스트와 CI
- **테스트 125개** (통합 테스트 중심 + 엔티티 상태 전이 단위 테스트)
- **Testcontainers**로 실제 MySQL 8.0 컨테이너에서 실행. 개발 DB와 분리되고, MySQL 고유 동작(NULL 유니크, 격리 수준, 락)을 그대로 검증할 수 있음
- 테스트 종류
  - 시나리오 테스트: 예약 조건, 조회 · 취소, 직원 예약, 상영 일정 변경 제한, 검색 · 상영시간표
  - **동시성 테스트**: 같은 좌석 10명 동시 예약 → 1명 성공, 같은 시간대 5건 동시 등록 → 1건 저장
  - **쿼리 수 측정 테스트**: N+1 개선 결과를 숫자로 고정
  - 회귀 테스트: 발견한 버그를 먼저 실패하는 테스트로 재현한 뒤 수정
- **GitHub Actions**: push · PR마다 전체 테스트 실행. JWT secret은 Repository secret으로 주입하고, 코드와 설정 파일에는 민감 정보를 값으로 두지 않음

## AI 활용 방식
Claude Code를 쓰되, **핵심 로직은 직접 작성하고 반복 작업은 AI에 맡기는** 원칙으로 진행합니다. 규칙은 [`CLAUDE.md`](CLAUDE.md)에 두고 AI가 매 작업에서 따르게 했습니다.

| 작업 방식 | 대상 | 진행 |
| --- | --- | --- |
| **[직접 구현]** | 새로운 개념의 첫 작업, 보안 · 동시성 · 결제 | 설계 방향 · 힌트를 받아 직접 작성 → AI 리뷰 |
| **[AI 초안]** | 이미 만든 패턴의 후속 작업, 테스트 | 리뷰 체크리스트 작성 → AI 초안 + 구현 의도 설명 → 직접 리뷰 · 수정 |

- AI는 작업 대상이 아닌 기존 코드를 고치지 않고 **보고만** 합니다. 이 규칙 덕분에 검색 테스트를 작성하던 AI가 기존 영화 수정 기능의 버그를 발견해 보고했고, 원인을 검토 · 보정한 뒤 직접 수정했습니다(트러블슈팅 3).
- AI 초안은 공통 리뷰 체크리스트([docs/review-checklist.md](docs/review-checklist.md))로 검토하고, 인증 · 예외 처리 · 트랜잭션 · 쿼리 코드는 방식과 관계없이 직접 확인합니다.
- 개발자 코드와 AI 초안은 커밋을 나누고, 테스트 통과 전에는 커밋하지 않습니다.

## 실행 방법
**필요한 것**: JDK 17, MySQL 8.0, Redis(기본 포트 6379), Docker(테스트용)

1. MySQL에 `cinema` 데이터베이스를 만듭니다. 테이블은 앱 실행 시 생성됩니다.
2. 환경변수를 등록합니다. 민감 정보는 설정 파일에 값으로 두지 않고 환경변수로만 참조합니다.

   | 이름 | 내용 |
   | --- | --- |
   | `CINEMA_DB_PASSWORD` | MySQL `root` 비밀번호 |
   | `CINEMA_JWT_SECRET` | JWT 서명 키 (HS256용, 32바이트 이상의 무작위 문자열) |

3. 실행
   ```bash
   ./gradlew bootRun
   ```
4. 테스트 (Docker 실행 중이어야 함, 개발 DB는 사용하지 않음)
   ```bash
   ./gradlew test
   ```
